## 三、实验整体逻辑分析

### 2.1 本章节的逻辑主线

本章围绕 **“最小可执行内核的构建与启动”** 这一核心主题展开。整个实验要解决的问题是：**如何在没有任何操作系统支持的裸机环境下，构建出一个能在 QEMU 模拟的 RISC-V 计算机上启动并输出信息的内核？**

操作系统本身无法把自己加载到内存中，因此需要依赖一层层的引导机制。本实验完整展示了这个过程：QEMU 加电 → OpenSBI 固件初始化 → 加载内核镜像 → 跳转到内核入口 → 内核初始化 → 输出信息。这个流程与真实 PC 的“UEFI → GRUB → 内核”三级跳本质上是同构的。

### 2.2 功能的逐步实现

本章实验按照 **“从底层到高层、从硬件到软件”** 的顺序逐步实现：

1. **首先搭建交叉编译环境** → 因为开发机是 x86 架构，而目标平台是 RISC-V，必须使用 `riscv64-unknown-elf-gcc` 进行交叉编译，这是后续一切工作的基础。

2. **然后编写链接脚本 `kernel.ld`** → 为了让 OpenSBI 能正确加载内核，必须明确指定内核的加载地址为 `0x80200000`，同时规定各段（`.text`、`.rodata`、`.data`、`.bss`）的内存布局。

3. **接着编写内核入口 `entry.S`** → OpenSBI 跳转到 `0x80200000` 时，CPU 还处于 C 语言无法运行的状态（栈指针未设置）。因此需要先用汇编设置好栈指针，再跳转到 C 语言入口。

4. **然后实现 `kern_init` 函数** → 这是内核的第一个 C 函数，负责清零 `.bss` 段，并调用 `cprintf` 输出启动信息。

5. **最后逐层封装输出功能** → 由于内核不能依赖任何库，`cprintf` 必须从最底层的 `ecall` 指令开始，依次封装 `sbi_call` → `sbi_console_putchar` → `cons_putc` → `cputch` → `cprintf`，最终实现格式化输出。

**为什么按这个顺序？** 因为每上一层都依赖下一层：没有交叉编译环境就写不出代码，没有链接脚本内核就加载不到正确位置，没有入口汇编 C 语言就跑不起来，没有底层 SBI 封装就无法输出信息。这是一条严格的依赖链。

#### 模块功能描述

**需要实现/修改的函数：**

```c
void kern_entry(void);            // 内核入口（汇编实现）
int  kern_init(void);              // 内核 C 入口
uint64_t sbi_call(uint64_t, uint64_t, uint64_t, uint64_t);  // SBI 调用封装
void sbi_console_putchar(unsigned char ch);                 // 单字符输出
void cons_putc(int c);                                      // 控制台输出封装
void cputch(int c, int *cnt);                               // 字符输出
int  cprintf(const char *fmt, ...);                         // 格式化输出
```

**功能说明：**

本模块负责内核的最底层启动功能，包括：
- 设置内核栈，为 C 语言运行准备环境
- 清零 `.bss` 段，初始化全局变量

涉及的模块包括 `kern/init/`（启动）、`libs/sbi.c`（SBI 封装）、`kern/driver/console.c`（设备驱动）、`kern/libs/stdio.c`（输出封装）。

### 练习1：理解内核启动中的程序入口操作

**负责人：** 2414006-王璞

**问题**：阅读 `kern/init/entry.S`，说明 `la sp, bootstacktop` 完成了什么操作，目的是什么？`tail kern_init` 完成了什么操作，目的是什么？

**解答**：

`kern_entry` 是内核的入口点，只有两条指令。

**（1）`la sp, bootstacktop`**：`la` 是伪指令（Load Address），在 RV64 下展开为 `auipc` + `addi` 两条指令。这条指令把 `.data` 段中符号 `bootstacktop` 的地址装入 `sp`（栈指针）寄存器。`bootstack` 到 `bootstacktop` 是链接器预留的内核栈空间，`bootstacktop` 位于栈顶（高地址端）。执行后 `sp` 指向栈顶，代表栈当前为空。

**目的是为后续 C 语言函数 `kern_init` 准备好栈环境**——C 语言编译后需要栈来保存局部变量、返回地址和临时数据，如果 `sp` 无效，进入 C 函数后会立刻崩溃。

**（2）`tail kern_init`**：`tail` 是伪指令，展开后是一条跳转指令。它的作用是跳转到 `kern_init` 函数入口，**且不修改返回地址寄存器 `ra`**。因为 `kern_entry` 是内核入口点只执行一次，`kern_init` 内部是死循环永不返回，所以不需要保存返回地址。使用 `tail` 代替 `call` 可以省去一条写 `ra` 的指令，是编译器的优化。

### 练习2：使用 GDB 验证启动流程

**负责人：** 2412953-裴家昌

**问题**：使用 GDB 跟踪 QEMU 模拟的 RISC-V 从加电开始，直到执行内核第一条指令（跳转到 `0x80200000`）的整个过程。RISC-V 硬件加电后最初执行的几条指令位于什么地址？它们主要完成了哪些功能？

**调试过程与观察结果**：

使用 `make debug` 启动 QEMU（`-S -s` 参数让 CPU 暂停并监听 1234 端口），再用 `make gdb` 启动 GDB 连接。

**观察一：复位向量处的指令**

GDB 首次连接时停在 `0x0000000000001000`。执行 `x/10i $pc` 反汇编，得到：

```asm
=> 0x1000:  auipc   t0,0x0
   0x1004:  addi    a2,t0,40
   0x1008:  csrr    a0,mhartid
   0x100c:  ld      a1,32(t0)
   0x1010:  ld      t0,24(t0)
   0x1014:  jr      t0
```

用 `x/2gx 0x1018` 读出 `0x1018` 处的值为 `0x0000000080000000`（OpenSBI 入口地址），`0x1020` 处的值为 `0x0000000087e00000`（设备树地址）。

**结论**：

RISC-V 硬件加电后最初执行的指令位于物理地址 `0x1000`（QEMU 模拟的复位向量地址）。这几条指令的功能是：
1. 用 `auipc` 获取自身地址 `0x1000`；
2. 用 `csrr` 读取硬件线程 ID（mhartid）；
3. 用 `ld` 从 `0x1018` 和 `0x1020` 读出预置的两个 64 位常量；
4. 用 `jr` 跳转到 `0x80000000`，将控制权交给 OpenSBI。

这段代码本身不做硬件初始化，只是一个“跳板”，负责把控制权移交给真正的固件。

**观察二：控制权移交给内核的瞬间**

用 `b *0x80200000` 在内核入口打断点，`c` 继续执行后，GDB 停在：

```
Breakpoint 1, kern_entry () at kern/init/entry.S:7
7           la sp, bootstacktop
```

此时 `pc = 0x80200000`，`sp = 0x80045e30`（OpenSBI 遗留的栈指针）。

**观察三：单步验证栈的切换**

执行一次 `si`（单步）后，`sp` 从 `0x80045e30` 变为 `0x80203000`，即 `bootstacktop` 的地址。再次 `si` 后 PC 跳到 `0x8020000a`（`kern_init` 入口）。

用 `print &bootstacktop` 返回 `0x80203000`，`print &bootstack` 返回 `0x80201000`，栈大小为 8KB（0x2000），与 `KSTACKSIZE` 一致。

**结论**：内核被 OpenSBI 加载到 `0x80200000` 并跳转执行。`kern_entry` 首先用 `la sp, bootstacktop` 把栈指针切换到内核专属栈，然后用 `tail kern_init` 跳入 C 语言入口函数。

## 六、实验总结与收获

### 对操作系统的理解

**1. 本实验重要知识点与 OS 原理知识点的对应关系：**

| 本实验知识点 | OS 原理对应概念 | 含义、关系与差异 |
|-------------|---------------|-----------------|
| 链接脚本 `kernel.ld` | 程序的内存布局 | 链接脚本描述各段（.text/.data/.bss）如何映射到内存。OS 原理中的内存布局是内核管理内存的基础，本实验只用链接脚本静态指定，尚无动态内存管理。 |
| 内核栈 `bootstack` | 进程/内核栈 | 栈用于函数调用时保存上下文。OS 原理中的栈是进程运行的基础，本实验只涉及内核启动阶段的内核栈，还没有用户进程栈。 |
| RISC-V 特权级（M/S/U） | 内核态与用户态 | M 模式运行固件，S 模式运行 OS 内核，U 模式运行用户程序。这是 OS 权限隔离的基础，但本实验只涉及 M→S 的切换，未涉及 S→U。 |
| `ecall` 指令 | 系统调用 | `ecall` 是主动触发异常实现特权级切换的机制。本实验中 S 模式用 `ecall` 调用 M 模式的 OpenSBI 服务，这与用户态通过系统调用进入内核态本质相同。 |
| OpenSBI 固件 | 引导加载程序 / 中断处理 | OpenSBI 是运行在 M 模式的固件，提供底层服务。对应 OS 原理中的 bootloader 和底层硬件抽象层。 |
| `sbi_console_putchar` | 设备驱动 | 封装了与底层硬件（串口）的交互。这是设备驱动的雏形，但本实验只涉及简单的字符输出，未涉及中断驱动的 I/O。 |
| `.bss` 段清零 | 进程内存初始化 | OS 加载程序时必须清零 .bss 段。本实验中 `kern_init` 手动调用 `memset` 清零，而 OS 原理中通常由加载器完成。 |

**2. OS 原理中重要但本实验未涉及的知识点：**

1. **虚拟内存与页表**：本实验内核直接使用物理地址（链接地址即加载地址），没有开启 MMU，也没有页表。虚拟内存是 OS 最核心的功能之一，将在后续实验中涉及。

2. **进程与线程管理**：本实验只有一个正在运行的内核，没有进程/线程的概念，也没有调度器。进程创建、切换、调度是 OS 原理的核心内容。

3. **中断与异常处理框架**：本实验虽然用到了 `ecall`，但没有完整的中断/异常处理框架（如中断向量表、上下文保存恢复）。后续 lab 才会系统实现。

4. **文件系统**：本实验没有任何文件系统，内核输出通过串口直接打印。文件系统是 OS 管理持久化存储的核心模块。

5. **同步与互斥**：本实验是单核、单线程执行，不涉及并发。OS 原理中的锁、信号量、条件变量等同步机制在本实验中完全没有出现。

6. **内存分配与回收**：本实验的内核栈是静态分配的（链接脚本预留），没有动态内存分配器（如 malloc/free、物理页管理器）。这些是后续 lab 的重点内容。

7. **用户态与系统调用接口**：本实验没有用户程序，也没有系统调用接口。OS 提供给用户程序的抽象（如文件、进程、信号）在本实验中完全没有涉及。

### AI 协作开发的经验

在本实验中，AI 工具主要发挥了以下作用：

1. **解释底层汇编与硬件机制**：例如 `entry.S` 中的 `la` 和 `tail` 伪指令、`0x1000` 复位向量的跳板代码，AI 能够结合 RISC-V 手册给出准确的逐条解释，降低了阅读底层代码的门槛。

2. **辅助调试环境问题**：当新版 QEMU 与旧版 Makefile 不兼容时，AI 能快速定位问题（`-device loader` 与 `-kernel` 的差异）并给出修复方案。

3. **整理报告结构**：AI 在实验报告的结构化表达、知识点对比方面提供了帮助，减少了整理素材的时间。

**最重要的经验**：AI 是工具，不是替代品。系统的核心逻辑（启动流程、特权级切换、内存布局）必须自己理解，否则答辩时无法自圆其说。AI 最适合用在“查资料”“解释概念”“排查环境问题”这类场景，而不是“帮我写完整个实验”。
